## 一、执行摘要

项目是一个**纯前端 D3.js 可视化作品**（无真正后端，"后端"即本地静态服务器），围绕"北京市空气质量与政策治理"主题，由一个外壳页 `index.html` 通过 iframe 整合 4 个相对独立的子项目：

| 标签页 | 目录 | 内容 |
| --- | --- | --- |
| 北京市空气质量概览 | `Project Milana/` | Three.js 3D 可视化 + 政策时间轴（含 Excel 客户端解析） |
| 政策措施分析 | `project_policy/` | 桑基图 + 措施词云 |
| 政策效果评估 | `project_time/` | 政策×污染物热力图 + 月度变化折线 |
| 国内与全球结果对照 | `project_chart/` | DiD 双重差分折线 + 城市对照 |

**总体评价**：前端工程与可视化呈现的**完成度和美学水准较高**（开场动画、标注避让、响应式、可访问性都做得用心），作为课程/作品集项目是合格甚至出彩的。但在**数据可信度、工程结构、性能与可维护性**三方面存在系统性问题，若要"产品化"或对外发布须先处理。

**最需要优先处理的 3 件事**：

1. **数据没有单一可信源**——同名核心数据文件 `beijing-air-quality.csv` 存在 3 份且内容已各自漂移（见 C1）。
2. **政策效果评估的"基准期"定义对早期政策不成立**，与界面文案矛盾，直接影响结论可信度（见 C2）。
3. **共享依赖散落在功能目录里被跨目录引用**，模块并不独立，牵一发动全身（见 M3）。

## 三、三轮检查问题清单（按严重程度）

### 🔴 严重（影响数据可信度，建议发布前必改）

#### C1. 核心数据 `beijing-air-quality.csv` 存在 3 份且已漂移，无单一可信源
存在 3 个同名文件，**MD5 与行数均不同**：

| 路径 | 行数 | 用途 |
| --- | --- | --- |
| `data/overview/beijing-air-quality.csv` | 4491 | 概览页（Project Milana）加载 |
| `project_chart/beijing-air-quality.csv` | 4496 | 对照页（`bar-chart-race.html:1292`）加载 |
| `data/project_time_pipeline/beijing-air-quality.csv` | 4496 | 数据管线中间产物 |

不同标签页消费的是**不同版本**的北京数据，可能导致同一指标在两个页面对不上。
**建议**：确立 `data/` 下唯一权威 CSV，各页面统一引用；管线产物与发布数据分离，用脚本生成而非手工复制。

#### C2. 政策效果评估的"政策前基准期"对 2014 年前启动的政策不成立
`data/policy_evaluation/policy_summary.csv` 中，首条政策《清洁空气行动计划》实际始于 2011-07（见 `data/overview/policies.csv:3`），但其 `baseline_year=2014`、`start_year=2014-01`——因为**数据本身始于 2014**。于是所谓"基准期"其实落在政策**执行期间**，而非政策之前。
而前端文案明确写着"色块比较政策开始前 12 个月平均值与结束年份平均值"（`project_time/page-language.js:74`）。对 2014 年前的政策，这一表述与实际计算口径不符，会让读者高估"政策带来的下降"。
**建议**：要么把这类政策标注为"数据起点受限，基准期非严格政策前"，要么在方法说明中明确区分"真·政策前基准"与"数据起点基准"，避免因果暗示。

### 🟠 重要（影响严谨性 / 体验，建议尽快处理）

#### M1. 2013 年数据为硬编码估算值覆盖真实数据，且未在图上标注
`project_chart/data-processor.js:115` 用 `seed2013 = { pm25: 89.5, pm10: 108.0, so2: 26.5, no2: 56.0 }` **强制覆盖** 2013 年聚合结果（注释：2013 仅 1 天数据不具代表性）。做法可理解，但图表（含 DiD 起点）把它当真实值呈现，未标注为估算。
**建议**：图例/脚注标明 2013 为文献估算；或 DiD 起点改用有完整数据的年份。

#### M2. SO₂ 原始缺失约 22%，经邻均填充但前端未披露不确定性
`data/project_time_pipeline/preprocessing-report.txt` 显示填充前缺失 `so2=990`（约占 4504 行的 22%），用"邻均 2 轮"补齐。大比例插值会显著影响 SO₂ 的年际趋势与政策评估结论。
**建议**：在 SO₂ 相关图表标注数据完整度/插值比例，或对 SO₂ 结论加保留性说明。

#### M3. 共享依赖散落在功能目录中被跨目录引用，模块并不独立
- `project_policy/d3.v7.min.js` 被 `project_time/policy-evaluation.html:61` 和 `Project Milana/index.html:8` 以 `../project_policy/d3.v7.min.js` 引用。
- `project_time/page-language.js` 被 `project_chart/bar-chart-race.html:3183` 跨目录引用。

任何一个功能目录的移动/改名都会让其它页面 404。
**建议**：新建 `vendor/`（第三方库）与 `shared/`（如 i18n、数据处理）目录集中托管，各页面统一引用。

#### M4. D3 加载方式不一致，部分页面依赖外网 CDN
`project_chart/bar-chart-race.html:13` 用 **CDN** 加载 D3；其余页面用本地副本；`Project Milana/index.html:651` 还从 CDN 加载 `xlsx`。导致：弱网/离线/受限网络下行为不一致，对照页与概览页可能加载失败。
**建议**：统一全部走本地 `vendor/`，确保离线可跑、行为一致。

#### M5. 概览页首屏负载过重（eager 加载）
外壳页对概览 iframe 用 `src`（立即加载），其余用 `data-src`（懒加载，`index.html:870-904`）。概览页随即拉取 ~2.6MB JS + 872KB 大图 + 16 张封面（实测日志佐证）。
**建议**：政策封面改为按需/懒加载与缩略图；`three.module.js` 走 ESM/按需；评估是否也对概览 iframe 延迟初始化。

#### M6. 数据来源标注引用了仓库中已删除的文件，可审计性退化
对照页脚注与代码注释仍写明数据取自 `delhi-city_day.csv` / `delhi_ncr_aqi_dataset.csv`（`bar-chart-race.html:1225-1227, 1309-1310`），但这两个原始文件在本分支已删除，新德里数据改为**内联硬编码**（`bar-chart-race.html:1313`）。读者无法再核对来源。
**建议**：保留精简后的来源数据，或把脚注改为"已预提取为内联常量，原始数据见 commit/外部链接"。

## 四、分模块点评

- **外壳 `index.html`**：开场粒子"除尘"动画 + 打字机 + 政策时间轴自动播放，叙事性强；tablist/aria/方向键导航的可访问性到位；iframe 懒加载思路正确。扣分项：政策数组硬编码且与 CSV 不同步（N3）、语言状态不持久（N10）。
- **`project_time`（政策效果评估）**：`app.js` 是全项目代码质量最高的部分——标注碰撞避让、tooltip 视口边界处理、响应式重绘、可访问的错误兜底都很专业。主要问题来自其消费的数据口径（C2、M2）。
- **`project_chart`（对照）**：DiD（京 vs 德里/对标城市）设计方向正确，注释对数据局限的标注相当诚实。问题在数据来源可审计性（M6）与命名（N2）。
- **`project_policy`（政策措施）**：桑基+词云结构清晰，配色分组用心；数据宜外置（N7）。
- **`Project Milana`（3D 概览）**：视觉最重，也是性能与依赖问题集中地（M4、M5），且自带独立 i18n（N4）、运行时 CDN 解析 Excel（宜预转 JSON）。

## 七、结论

这是一个**呈现层优秀、数据与工程层需要补课**的可视化项目。视觉与交互已达到对外展示水准；但"数据可视化"的可信度根基——单一数据源、口径一致、方法学表述准确——存在 2 个严重问题（C1、C2）必须先解决，否则精美的图表反而会放大错误结论的传播。建议按上面的 P0→P1→P2 路线推进，先稳"数据与表述"，再优化"结构与性能"。
